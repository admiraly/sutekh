## 2. Design in brief
- Per world the supervisor keeps: fixture path and sha256; creation capsule/source sha256 and project paths; up to `checkpoint_retain` checkpoints (sha256, revision, tick, schedule, snapshot bytes as spool file `<sha>.snap`); the log of accepted ops since the newest checkpoint (`step` with ticks completed, `install` with candidate id, system revision, effective tick, semantic hash), each with revision and digest after it.
- Digest = SHA-256 of the canonical snapshot bytes (includes the world revision). Partial step progress is logged from the digest, so a failed step cannot desynchronise the log.
- Recovery: new worker (`replaced_pid_new`), `internal.world.seed` (no id reuse), per world `world.create` with `world_id` and the spool capsules (hashes checked by the worker), `internal.world.restore_bytes` exact at the checkpoint revision (file sha256 checked), digest check, log replay (`world.step`, `internal.candidate.install` from spool with evidence `passed`), digest check after each op, final check against the acknowledged state. Any mismatch marks the world `unrecoverable`.
- Crash bookkeeping: identical in-flight operation (kind, world, acknowledged tick, candidate) on consecutive recoveries counts; at `quarantine_after` (2) the revision is quarantined (install: refused from then on; other ops: rollback to the newest checkpoint predating the installed revision, recorded as a new revision, post-checkpoint ops discarded and reported).
- The request that found the death is not executed; it gets `SU_E_WORKER_FAILED` (retry true) and `recovery`. No automatic retry of any request.

## 3. Limits (defaults; `SuAgentConfig`)
`checkpoint_interval_ticks` 64; `checkpoint_retain` 4 (max 8); `log_max_entries` 256 (max 1024; reaching it forces a checkpoint before the next op); `quarantine_after` 2; `spool_bytes_max` 32 MiB (capsules, sources, checkpoints; a world's checkpoint reservation = bound(rows, fields) x (retain+1) is checked at creation); `spool_dir` (NULL: private mkdtemp dir, removed at exit). Recovery attempts per request: 3.

## 7. Deviations for the contract owner
- `world.restore` is not a log entry: the restored state is checkpointed at once and the log restarts from it (documented in AGENT_RPC section 8). The spec listed it as a log entry.
- Client `world.snapshot` now returns `capture_ns: null` (the capture is no longer timed in the worker).
- Client `world.restore` can name only the supervisor's retained checkpoints (4 per world). Older ids return `SU_E_INVALID_ARGUMENT` (the worker kept 8).
- `world.close` `released.snapshots` counts retained client-taken snapshots (M0 meaning); `released.systems` is the worker's count.
- `candidate.install` and client `world.restore` still re-check project files against their recorded hashes (M0 rule). Recovery uses the spool only, so a changed project file does not affect recovery.
- The crash seam lives in `tests/recovery/recovery_worker` (the production worker entry built with `SU_TEST_FAULT_HOOKS`), not in `worker_stub`.
- Installs are checkpointed as the spec says. The install-replay path is covered by the test-only `no_install_checkpoint` knob.

## 8. Unrun checks and limits
- Clang build and clang sanitizers: not run (runtimes not installed here, as in earlier handoffs).
- Windows: not implemented (POSIX only).
- Recovered `txid`s and the worker registry differ from an uninterrupted run (worker-local); canonical state, revisions, ticks and columns are identical.
- A fixture file changed on disk after creation makes its world unrecoverable (fail closed).
- Replacement workers inherit the supervisor's environment; the seam variables are read only by test-built workers.
- Recovery replays through the public worker methods, so cost grows with the log (bounded by `log_max_entries`) and with the checkpoint size (bounded by the reservation).
- Quarantine rollback discards accepted operations after the target checkpoint; they are reported as `discarded_ticks`, not replayed.
- Candidate evaluation workers are unchanged and remain disposable.
