# M2-00 contract review (r1)

Reviewed: `planning/contracts/M2_ENTITIES_CONTRACT.md` (commit 7e4a08f), `include/sutekh/entities.h`, `include/sutekh/status.h`.
Reviewer: independent verifier. Scope: report only. No edits to `include/` or `planning/contracts/`.

## Verdict: REJECT as written (repair as r2)

The header-level pieces are correct and compile. The contract does not yet fix enough of the ABI, storage, verifier and snapshot behaviour for an implementer to build without guessing, and several rules cannot be implemented as stated. Each blocking item below needs an owner decision or a wording change before implementation starts.

## Blocking

**B1. Dead-slot masking cannot be implemented as written.**
- The reference VM loop (`src/vm/su_vm.c:431-457`) runs over `rows` with no alive input. Skipping dead slots needs an alive mask in `SuInvocation`. That is an `abi.h` change, which AGENTS.md reserves for the owner.
- Native IR 0.1 kernels "may process dead slots", but `su_world_commit_staging` (`src/world/su_world.c:400-439`) does a whole-column `memcpy`. There is no alive mask, so a dead slot can receive a nonzero staged value and break canonical zero.
- The contract never says when a despawned slot's columns are zeroed. That must happen in the working root after systems, before publish.
- Wording: "An alive mask (one u32 per row, 0 or 1) is passed in `SuInvocation` (new ABI version). `su_world_commit_staging` copies only alive rows; dead rows keep canonical zero. Despawn zeroes all columns of the slot in the working root in the boundary step, before publish. Spawn writes init fields and schema defaults to all other fields."

**B2. Canonical-dump contradiction.**
- Section 1 says IR 0.1 dumps "stay identical". Section 4 says snapshot columns cover all slots, dead included.
- Capacity is rounded up to 1024-slot chunks, so the 4-entity fixture becomes 1,024 rows. The current `SUWSTATE` encoding (`su_world.h`, `su_world.c:590-660`) is row-count based and would change.
- Wording: "Canonical state encoding becomes `SUWSTATE` encoding_version 2 over `capacity` rows, adding per-slot generation and alive bytes. Dumps of IR 0.1 fixtures therefore change; the new expected dumps are stored and listed in the handoff. (Alternative: encode only the prefix up to the highest alive slot. Owner picks; the choice must be stated.)"

**B3. Capacity limit is unsatisfiable.**
- `SU_LIMIT_ROWS` is 1,000,000. Rounded up to whole chunks it becomes 977 x 1024 = 1,000,448, which exceeds the limit.
- Also undefined: where `max_entities` comes from. `world.create` and the fixture format (`examples/world.json`) have no capacity field.
- Wording: "`capacity = ceil(n / 1024) * 1024`, and `capacity <= floor(SU_LIMIT_ROWS / 1024) * 1024` (= 999,424). `world.create` accepts optional `max_entities` (default: n); fixtures omit it."

**B4. Chunk definitions disagree with the scheduler.**
- Section 1 says chunks of `SU_CHUNK_SLOTS` (1024) are the unit of M1 parallel work. The actual scheduler derives chunk size from `rows / SU_JOBS_TARGET_CHUNKS`, with a minimum (`src/runtime/jobs/su_jobs.c:15-22`).
- Wording: "Structural/event buffers are per storage chunk (`SU_CHUNK_SLOTS`). Scheduler job slicing (`chunk_rows`) is independent; it may be set to `SU_CHUNK_SLOTS` but is not required to be."

**B5. Headers the contract depends on do not exist.**
- `ir.h` defines opcodes 1..9 only. Opcodes 10..14 are absent.
- `SU_IR_VERSION_STRING` is `"0.1"` (`ir.h:8`). The verifier hard-codes `SU_IR_VERSION "0.1"` (`su_lir.c:13-15`) and rejects any other value at stage 4.
- `SU_ARTIFACT_FORMAT_VERSION` is a single constant (`ir.h:10`) used in the hash preamble (`su_lir.c:690`), in `su_lir.c:875`, `su_agent.c:1927`, `sutekh_main.c:36` and `native/abi.h:64`.
- `SU_SNAPSHOT_FORMAT` is `"0.1"` (`snapshot.h:32`).
- `SU_EVENT_REJECTED` and the reserved range for event kinds are not defined. The contract text uses the name, but `entities.h` has no definition.
- Wording: "Owned header changes (owner approval required): `ir.h` adds `SU_IR_VERSION_STRING_0_2 "0.2"`, `SU_OP_SLOT_U32 10`, `SU_OP_GEN_U32 11`, `SU_OP_TICK_U32 12`, `SU_OP_DESPAWN_SELF 13`, `SU_OP_EMIT_EVENT 14`, `SU_ARTIFACT_FORMAT_VERSION_0_2 2`. `entities.h` adds `SU_EVENT_REJECTED` and `SU_EVENT_KIND_RESERVED_MAX`. `snapshot.h` adds `SU_SNAPSHOT_FORMAT_0_2 "0.2"`. `abi.h` adds the alive mask and per-chunk buffer bindings (B1, B8)."

**B6. IR 0.2 operand encoding is not specified.**
- `emit_event` takes four operands (cond, kind, a, b). `SuInsn` has `dst, a, b, c`.
- `kind` is a constant, not a register. A constant of `0xFFFFFFFF` collides with `SU_OPERAND_NONE`.
- `tick_u32` says "the tick being computed". Whether that means `tick + 1` or the committed tick is not stated.
- Wording: "`emit_event`: `dst` = cond reg, `a` = kind (const u32, any value), `b` = a reg, `c` = b reg. Kind is never interpreted as an index. `tick_u32`: defines `committed_tick + 1` (the tick being computed) mod 2^32."

**B7. Capsule limit keys conflict with the schema.**
- `schemas/capsule.schema.json` sets `limits.additionalProperties: false` and requires exactly `max_instructions`, `max_rows`, `allocation`. The new `max_struct_per_row` / `max_events_per_row` keys would be rejected.
- The per-tick caps (`max_struct_per_tick`, `max_events_per_tick`) have no declaration site at all.
- Wording: "Schema owner approves an extension: `limits` gains optional `max_struct_per_row` and `max_events_per_row` (integers 0..64, default 0; 0.1 capsules must not declare them). Per-tick caps are world-creation config (`max_struct_per_tick`, `max_events_per_tick`), not capsule keys."

**B8. Per-row cap counting and buffer allocation are undefined.**
- A loop-free IR runs each instruction once per row, so the worst case is the count of `despawn_self` plus `emit_event` instructions, whether or not their `cond` is true. The contract should say this in those words.
- `allocation: forbidden` (schema) and LIVE_IR section 5 forbid mid-tick allocation, so the per-chunk buffers must be sized at admission. The sizing formula is not given.
- Wording: "Worst-case emissions per row = count of `despawn_self` + `emit_event` instructions (conditions ignored). Verifier: declared cap < worst case -> `SU_E_RESOURCE_LIMIT` at stage 5 (capsule limits, same stage as `max_instructions`), not stage 6. Buffer size per chunk = `SU_CHUNK_SLOTS * max_per_row` entries, preallocated at admission."

**B9. Multi-worker 0.2 execution is unspecified.**
- `su_jobs` runs chunks on worker threads, each calling `su_vm_invoke_v1` with a per-worker context (`su_jobs.c:320-356`). Writing structural or event records from those threads needs per-chunk buffers, and the contract does not say so.
- Wording: "IR 0.2 modules run as one job per chunk into per-chunk buffers; the merge at the boundary is canonical order. Any worker count yields identical output (tests T-M2-04)."

**B10. Event and command semantics are incomplete.**
- Do rejected commands consume event_seq and event-log capacity? Are they counted against per-tick caps?
- Which `system_index` do control-plane `world.spawn`/`world.despawn` use? Is their order relative to IR commands at the same boundary defined?
- `events.read` cursor: is it an `event_seq`? What does a reader get when the cursor predates eviction?
- Source of `event_log_max`.
- Wording: "Rejected commands emit a `SU_EVENT_REJECTED` record at their canonical position, consume `event_seq`, and count toward `max_events_per_tick`. Control-plane commands use `system_index = 0xFFFFFFFF`, ordered before IR commands. `events.read` cursor = `event_seq`; if the cursor is below the oldest retained seq, the reply has `dropped` > 0 and starts at the oldest retained record. `event_log_max` is world-creation config."

**B11. Spawn is undefined.**
- No template contract exists, so "template-declared init fields" has no referent. The header `arg` is u64, but a template id width is not stated.
- `su_world_create` rejects entity id 0 (`su_world.c:253-257`), but spawned entities carry id 0 by contract.
- Wording: "M2-00 spawn is accepted only as a control-plane request with `template_id` in `[1, 2^32)`; no template table exists in M2-00, so every spawn returns a rejected record (`SU_EVENT_REJECTED`) until the templates contract lands. Entity external id 0 is permitted for slots created by spawn; `su_world_create` keeps rejecting 0 for fixture ids."

**B12. Handle validation rules have gaps.**
- `SU_ENTITY_MAKE(5, 0)` is `5`, not the invalid sentinel. The contract says "zero" is stale but does not state that any handle with generation 0 is stale.
- The stored generation after retirement is unspecified. Per the header, `SU_GEN_RETIRED` must be stored, with `alive = 0`.
- Slot >= capacity: `SU_E_STALE_HANDLE` or `SU_E_INVALID_ARGUMENT`? The contract is silent.
- Wording: "A handle is stale (`SU_E_STALE_HANDLE`) if its generation is 0, its slot is >= capacity, its slot is dead, or its generation differs from the slot's. A retired slot stores `generation = SU_GEN_RETIRED`, `alive = 0`."

**B13. Snapshot 0.2 and 0.1 compatibility is unspecified.**
- Restore currently requires the snapshot's `entity_ids` to equal the target world's (`snapshot.c:876`).
- The body must re-encode byte for byte (`snapshot.c:945-955`). A 0.2 emitter needs an exact key order and layout for `slots`, `event_log` and `dropped`. The contract gives no layout.
- A 0.1 snapshot restored into a world with capacity > n: which capacity? The contract does not say how the target's capacity is chosen.
- Wording: "0.1 restore: the target world's capacity must equal `ceil(n/1024)*1024`; slots `0..n-1` take the snapshot's external ids with generation 1 and alive 1; the rest are dead generation 1 (never issued). The 0.2 JSON key order is fixed in the contract as an appendix with an example."

**B14. Hash encoding interplay.**
- The artifact format is hashed as a single constant (`su_lir.c:690`). "Bumped to 2 only for 0.2 modules" needs a per-module format value, not the global constant.
- The byte layout of the 0.2 additions (opcode words, queue limit fields) is not given. "Capsule queue limits" enter the hash for 0.2 only, but the order and widths are not specified.
- Wording: "For `ir_version` 0.1 the hash input is byte-identical to the current encoding (test vector: the M0 fixtures' semantic hashes unchanged). For 0.2 the hash inserts `ir_version` string, then `max_struct_per_row` u32, `max_events_per_row` u32 after the field table, then the instruction count and words as today. Artifact format for 0.2 = 2."

**B15. Verifier stage placement is not complete.**
- A 0.2 op under `ir_version` "0.1" must be `SU_E_UNKNOWN_OPCODE` (stage 6). The contract does not say so.
- Stage 4 must accept `"0.2"` and keep rejecting other values. The contract does not say so.
- Over-declared caps belong to stage 5 (see B8), not stage 6.
- Wording: "Stage 4 accepts `ir_version` in {`0.1`,`0.2`}. Stage 6: an IR 0.2 opcode in a 0.1 module -> `SU_E_UNKNOWN_OPCODE`. Stage 5: per-row cap declaration below worst case -> `SU_E_RESOURCE_LIMIT`. Stage 6: `emit_event` kind constant out of range -> `SU_E_TYPE`."

**B16. Control-plane methods are not specified.**
- No request or reply schemas, error mapping or ordering for `world.spawn`, `world.despawn`, `events.read`, and the `world.create` fields added by B3 and B10.
- Wording: the contract must list each method with params, reply fields, and error codes. Until then, implementers must not add them.

## Non-blocking

- `status.h` is correct: `SU_E_STALE_HANDLE` = 21, `SU_STATUS_COUNT` = 22, name table complete.
- `SuStructCmd` (32 bytes, `arg` at 16) and `SuEvent` (40 bytes, `kind` at 16) match their static asserts.
- `SU_ENTITY_MAKE`, `SU_ENTITY_SLOT` and `SU_ENTITY_GEN` are correct at every boundary tested (see below).
- A `static inline` status name helper triggers clang `-Wunused-function` when `status.h` is compiled as the main file. This is an artifact of that compile mode; it does not occur in a normal translation unit.
- Add mutation proofs for the verifier's stage-order rules (B15).
- The "dead slot canonical zero" test should cover a dead slot that receives a staged nonzero from a native kernel (B1).
