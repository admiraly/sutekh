## T09 reason (exact)
The real binary cannot produce a runtime failure in a second system after the first succeeded. Capsule `limits.max_rows` is not enforced at runtime: `src/runtime/schedule.c` never calls `su_vm_context_set_row_limit`, so the VM uses `SU_LIMIT_ROWS` = 1000000. Observed: `demo.movement_b` with max_rows 2 over a 4-row world was accepted by world.create and a step published tick 1 with both systems applied. Row count is shared by all systems in a world, so a size limit cannot fail only the second system. No other runtime fault path was found in `src/vm`. The admission side was checked and passes: a second system that fails verification (wrong_permission) is refused by multi-system world.create with SU_E_UNDECLARED_WRITE.
Owner: engine (max_rows not enforced; a contract decision is needed on whether it is enforced per system).

## T10 scope
candidate.evaluate is synchronous, so the kill comes from a harness thread polling `/proc/<supervisor>/task/*/children`. Passed on attempt 0 in the final run: child killed mid-evaluation, reply SU_E_WORKER_FAILED, candidate.status worker_pid equals the killed pid, supervisor answers, active worker pid, world state and manifest unchanged, world still steps. Limitation: the kill is racy; attempts where the reply won are recorded and retried; with no kill landed the test is not_run, never passed.
