## Behavior notes
- Field table is sorted ascending by id at creation; views list readable fields (READ bit) and writable fields (WRITE bit) in that order.
- Reads during a tick come from the working root; writes go to staging; `su_world_commit_staging` copies staging into working for an explicit list of field IDs (validated before any copy). `su_world_publish` copies working to committed and increments tick. `su_world_abort` only leaves the tick, so committed is never touched.
- `su_world_init_committed` seeds committed values, allowed only at tick 0 outside a tick (fixture loading).
- Canonical dump: committed root only, little-endian, no names or padding (layout in `su_world.h`). `su_world_state_equal` compares these bytes.
- Error codes: NULL or wrong phase -> `SU_E_INVALID_ARGUMENT`; non-u32 type -> `SU_E_TYPE`; duplicate ID/name or unknown field -> `SU_E_SCHEMA_MISMATCH`; row/field count over `SU_LIMIT_*`, names over 255 bytes, size overflow, or allocation failure -> `SU_E_RESOURCE_LIMIT`; commit of a read-only field -> `SU_E_UNDECLARED_WRITE`.
- Entity IDs must be nonzero and unique (zero is reserved per DATA_ABI_AND_STORAGE section 1; uniqueness is my addition).

## Contract ambiguities
1. Entity ID width: the contract does not say. I used u32 (the table is u32 storage). If stable IDs must be wider, the canonical dump and creation signature change.
2. Field ID zero: not stated as invalid for fields; currently allowed.
3. Allocation failure maps to `SU_E_RESOURCE_LIMIT`. No code for out-of-memory exists in the status list.
4. Access 0 (a field with neither READ nor WRITE) is rejected as `SU_E_INVALID_ARGUMENT`. Not in the contract.
5. Name length cap (255 bytes) is my choice; the contract says nothing.
