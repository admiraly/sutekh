# M0-00 independent review (contract generation 1, ABI v1, SU-LIR 0.1)

Scope: `include/sutekh/{status,ir,abi}.h`, `planning/contracts/M0_CONTRACT.md`, `examples/*.json`, `examples/invalid/*`, read against `AGENTS.md`, `ENGINE_CONSTITUTION.md`, `LIVE_IR_SPEC.md`, `docs/AGENT_RPC.md`, `docs/DATA_ABI_AND_STORAGE.md`. No files under `include/` or `planning/contracts/` were edited.

## Verdict

**accept-with-changes.**

The headers compile cleanly under strict C17 with gcc and clang, and the static layout asserts hold. The prose contract, however, leaves several decisions open (field operand meaning, binding order, store rule, hash encoding, context lifecycle, error mapping) that a parser, VM, or world implementer would have to guess. These need one revision to M0_CONTRACT.md and minor header comments before consumers build against them. No header layout change is required.

## Blocking issues

1. **Field operand: index or ID?** `ir.h` says `SuInsn` field operands are "indices into the capsule's verified field table, never names". M0_CONTRACT §5 says the canonical hash replaces field operands "by field id". The movement fixture happens to make index and ID coincide (IDs 1,2 at indices 0,1), which hides the conflict. Pick one: store the table index in `SuInsn` and map index to ID when hashing.
2. **Who owns field IDs?** LIVE_IR §6 says the contract binds to "stable schema field IDs" and declaration order is not identity. In practice `movement.capsule.json` assigns the IDs (1, 2). There is no schema file for `demo.actor`, and `world.json` keys columns by name. Two capsules could give the same field different IDs. Name the authoritative table.
3. **`SuInvocation.bindings` order.** The comment says `bindings[i]` "corresponds to field table entry i ... for readable fields only", which is self-contradictory when write-only fields exist. Specify: field-table order filtered to READ, matched by `field_id`.
4. **Store rule.** LIVE_IR §5 requires every writable field to be stored "exactly once", but also says unchanged fields are "not copied through registers unnecessarily". For a write-declared field that is unchanged, the two rules conflict. Decide whether it must be stored (copy) or must not be declared writable.
5. **Verifier error policy and missing code.** A writable field that is never stored has no error code in the set 1..19. Also undefined whether the verifier stops at the first fault or collects all. Most negative fixtures contain several faults (see non-blocking 3), so the expected code is only meaningful under a stated policy.
6. **Staging and context lifecycle.** Undefined: whether commit is a copy or a pointer swap; whether "no aliasing" means pointer equality or range overlap (overlap is required); and how `SuExecContext` is created, sized, and destroyed. There is no prototype for it, and the per-row register file has no declared capacity. M0-04 cannot allocate scratch "at admission" without this.
7. **Wrapper error mapping is incomplete.** ABI says violations return `SU_E_INVALID_ARGUMENT` or `SU_E_SCHEMA_MISMATCH` without assigning length mismatch, aliasing, stride/access mismatch, or NULL ctx. `rows > SU_LIMIT_ROWS` is `SU_E_RESOURCE_LIMIT` in M0_CONTRACT §4 but unlisted in the ABI. "Oversize message framing" is mapped to both `SU_E_PARSE` and `SU_E_RESOURCE_LIMIT`.
8. **Hash encoding gaps** (M0_CONTRACT §5). Unspecified: length-prefix width and UTF-8 for strings; mapping of `"u32"` to `SU_TYPE_U32` and `read/write` booleans to `SU_ACCESS_*`; register numbering base (0 or 1); which bytes `source_hash` covers (IR, capsule, or both); whether `layout_generation` belongs in the semantic hash (a layout-only bump would change it); whether `query` is the IR's or the schema ID; whether the field table is declared fields or referenced fields; duplicate field IDs (no error code); and LIVE_IR §9's "referenced definition hashes", which the encoding omits. Schedule, limits, and tests are excluded without being stated.
9. **Snapshot (M0_CONTRACT §6) is under-specified.** Unclear: `snapshot_format` value; whether `columns` keys are names or IDs; widths of `tick`, `world_revision`, `entity_ids`; whether restore assigns a new revision.

## Non-blocking issues

1. `SuColumnBinding.data` is `void *` for inputs as well as staging; read-only inputs should be `const void *` or the comment should say the wrapper enforces read-only.
2. `SU_OPERAND_NONE` and `UINT32_MAX` are used interchangeably; the sentinel equals a legal const value `0xFFFFFFFF` (meaningful only by opcode).
3. Negative fixtures are multi-fault: `undeclared_write` (no store to `position_x`), `duplicate_register` (`v` undefined), `undefined_register`, `unknown_opcode` (`next` undefined at store). Only one code is checked per file.
4. `negative_u32.lir.json` (`-1`) is valid JSON syntax; expected `SU_E_TYPE` is a choice the spec does not state. Schema validation rejects it before semantic checks, so the schema-to-code mapping is undefined. Same for `unknown_opcode`.
5. No fixtures for `UNDECLARED_READ`, missing store, schema/layout-generation mismatch, limits, duplicate field ID, bool passed to `add_u32`, unknown key, or alias.
6. `eq_u32`/`lt_u32` operand type (must be u32, not bool) is not stated in the `ir.h` table.
7. `SU_LIMIT_ROWS` is a fixed `#define`, while LIVE_IR §7 calls the limits configurable.
8. AGENT_RPC §5 lists the error set without 18/19 and gives no error-object shape; there is no distinct code for unknown method names.
9. Diagnostic record (LIVE_IR §8: path, JSON pointer, span, expected/actual, hint) is not pinned; fixtures check codes only.
10. Zero writable fields: whether `binding_count = 0` is valid is unstated.
11. `failed_insn` gives no row index.
