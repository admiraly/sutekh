# Issue 174: SDL3 audio output backend for non-Windows builds

## State and scope

Locally verified on `linux-audio-sdl3`, based on `d2f0e72` (origin/main, merge of PR 173). PR for issue 174. Not
merged.

`su_audio_device_open` had only the WASAPI backend, so on Linux it returned `SU_E_UNSUPPORTED_METHOD` and the mixer
rendered to nowhere: a downstream game that develops and playtests on Linux had no sound. Now:

- `src/audio/su_audio_sdl3.c` (new) is the non-Windows backend: SDL3's default playback device, float32 stereo at
  the mixer's rate with SDL converting to the device's own format and rate, driven by SDL's audio thread, which
  calls back once per device period (`SDL_OpenAudioDeviceStream`) instead of a render thread of ours. The SDL3
  library is opened at run time with `dlopen` (`libSDL3.so.0`; `SUTEKH_SDL3_LIBRARY` overrides), exactly as
  `src/platform/window_sdl3.c` does, with the same compile-time signature check against the pinned 3.2 headers.
  Nothing links against SDL; a build without the headers keeps `src/audio/su_audio_nodevice.c`.
- The SDL audio stream is the render-ahead buffer this backend owns, the counterpart of the WASAPI device buffer's
  padding: each callback tops the stream up to two device periods of input, so one stays queued while the device
  consumes one. A callback that finds the stream empty is a starvation: it counts in `empty_buffers` and gets the
  same 64-frame de-click fade as the WASAPI zero-padding path, in mixer and PULL mode alike. The render buffer is
  allocated once at open (four periods plus the fade); the callback allocates, locks (beyond the stream's own
  reentrant lock) and blocks on nothing.
- `SuAudioDeviceStats` keeps the WASAPI contract: `callbacks`, `callback_us`/`callback_max_us`/
  `callback_over_budget`/`frames` per submission (entry through `SDL_PutAudioStreamData`), `interval_us` between
  callback entries, `empty_buffers`, `backend_errors` (failed stream write, or a device buffer that outgrew the
  render buffer). `wait_timeouts` stays 0: this backend waits on no event, SDL paces its thread.
  `SuAudioDeviceInfo.buffer_frames` is the device buffer in the stream's (the mixer's) frames and `latency_ms` is
  the device buffer plus the queued period, computed at open; SDL reports no latency of its own. The endpoint name
  carries SDL's driver in parentheses (`pipewire`, `pulseaudio`, `alsa`, `dummy`).
- Missing SDL3 library, missing audio driver/device and a build without the backend each return the defined
  `SU_E_UNSUPPORTED_METHOD` with a message that says which.
- `cmake/SutekhPresentation.cmake` now searches the SDL3 headers once, for the window and the audio backend, so
  `SUTEKH_WINDOW=OFF` no longer hides them from audio; `su_audio` gets the include directory (SYSTEM, PRIVATE) and
  `${CMAKE_DL_LIBS}` only when the SDL3 backend is compiled in.
- `tests/audio/test_audio_device.c` (the existing smoke test) now waits for the first rendered block before
  measuring its 0.4 s of audio: a PipeWire node takes about 200 ms to connect before its first pull, and the old
  window counted that as audio that never played. The assertion itself is unchanged.

New tests (CMake names):

- `audio_device_backend` (every non-Windows build): a missing SDL3 library gives `SU_E_UNSUPPORTED_METHOD` with a
  message naming the library, no device, zeroed stats and no crash; then the default device is opened, or refused
  with a message (headless CI). Also checks the argument validation and the null-device helpers. A build with the
  nodevice backend checks its own refusal.
- `audio_device_backend_no_driver` (SDL3 backend only): the same binary as `--no-driver` with
  `SDL_AUDIO_DRIVER=sutekh-no-such-driver`, which must be refused with a message about SDL's audio subsystem. SDL
  reads the environment once, on its first call, so this needs its own process.
- `audio_device_sdl3` (SDL3 backend only, skip 77 without the library): `SDL_AUDIO_DRIVER=dummy`, a real
  open/render/close. Mixer mode plays a looping tone and checks the info fields, that `su_audio_device_frames`
  advances, that the mixer rendered what the device took, and the stats contract (one histogram sample per
  callback, maxima within the totals, no backend errors, stats agreeing with the info). PULL mode, as the
  integrated runtime opens it, renders 100 ms and checks the same.
- `audio_device_sdl3_alloc` (SDL3 backend only, skip 77 without the library): the same source with the backend
  compiled against counting allocators (`malloc=sdl_test_malloc`, ...), like `audio_callback` and
  `audio_graph_alloc`. Opening must allocate (the positive control that the seam is wired in), then 100 ms of
  callbacks must allocate nothing.

## Unrun / limits

- Windows (WASAPI) is unrun: no Windows toolchain here, and CI has none for this change. `su_audio_wasapi.c`,
  `test_audio_device.c`'s Windows path and the CMake `WIN32` branches were not compiled. The change to
  `test_audio_device.c` is portable C (no POSIX call added).
- PulseAudio, ALSA, JACK and sndio backends of SDL were not exercised; only PipeWire and dummy ran. macOS uses the
  same code and is untested.
- No acoustic or loopback measurement, and no long run: the reported latency is computed (device buffer plus the
  queued period), not measured, and no device numbers are published.
- Device loss at run time (a PipeWire node disappearing, a device migration) is handled by SDL and was not
  exercised; `su_audio_device_close` still works, but the stats after a loss were not checked.
- The 200 ms PipeWire start-up is measured, not explained: `audio_device` waits for the first block instead of
  counting it. No attempt was made to reduce it.
- `-DSUTEKH_SANITIZE=thread,memory` and the native (AsmJit) tier were not run.
- The pre-existing `window_swapchain_xvfb` LeakSanitizer report (libSDL3 X11/Mesa) is untouched; it is the only
  sanitizer failure and reproduces at the base commit.
