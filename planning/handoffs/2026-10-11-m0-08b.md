## 2. Methods (AGENT_RPC style, forwarded by the agent to the active worker)

`world.snapshot {world_id, expected_world_revision}` -> `{snapshot_id, world_revision, tick, bytes, sha256, capture_ns|null}`
- The world revision is unchanged. `sha256` equals `snapshot_id` (SHA-256 of the canonical bytes).

`world.restore {world_id, snapshot_id, expected_world_revision}` -> `{world_id, world_revision, tick, restored_from, worker_pid, semantic_manifest}`
- `world_revision` is a NEW revision. `restored_from` is the snapshot id. `semantic_manifest` is taken from the schedule the restore installed (registry txids, system revisions).

Errors:
- Stale expected revision: `SU_E_STALE_REVISION`, checked before any other work.
- Unknown, evicted, or other-world `snapshot_id`: `SU_E_INVALID_ARGUMENT`, message "unknown or evicted snapshot_id for this world". The contract does not define a dedicated code. Contract owner, please confirm or amend.
- Snapshot parse failures (`SU_E_PARSE`, `SU_E_TYPE`, `SU_E_DUPLICATE_KEY`): passed through from `su_snapshot_parse`.
- Schema or manifest mismatch, or a revision whose bytes no longer match the recorded hashes: `SU_E_SCHEMA_MISMATCH`.
- Any failure leaves the world, its schedule, and its installed registry records unchanged.
- `world.snapshot` of a world inside a tick cannot happen here: the worker runs ticks synchronously, so the capture never sees an open tick.

`engine.info` capabilities now also list `world.snapshot` and `world.restore`.

## 3. Design

- Checkpoint store: one `su_checkpoint_store_create(0)` per worker (retain 8). Ids are monotonic. Eviction is FIFO.
- Per-checkpoint record (8 slots, same retention): world id, snapshot id, and for each system its id, semantic/source/capsule hashes, and the supervisor-resolved capsule and source paths. Paths are kept per schedule slot (`WorkerWorld.paths`) from `world.create` and each successful `candidate.install`.
- Restore sequence:
  1. Stale check.
  2. Find the record and store entry.
  3. Strict parse against the current schema (`su_snapshot_parse`).
  4. Rebuild the schedule by reloading each recorded revision with `su_reload_load` and its recorded hashes. Check the manifest order, ids and semantic hashes. Check the field table is unchanged.
  5. Build the new world with `su_snapshot_restore`.
  6. Registry: a system whose semantic hash changed gets a new txid (`"restore"`), installed at the snapshot tick, with the old revision retired.
  7. Swap the world and schedule. Nothing after the swap can fail.
- Consequence: restoring a snapshot taken before a code swap also restores the old code and manifest (test `test_swap_restore`).
- Shared snapshot ids (identical states captured twice): the newest record wins.
