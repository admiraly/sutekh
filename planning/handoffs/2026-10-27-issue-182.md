# Issue 182: a 64-bit lane in a cross-table target set

## State and scope

Branch `fix-target-64bit-lanes`, based on `origin/main` `b560c8e` (merge of PR #178). Locally verified; integration
pending.

Exact modified paths:

- `src/host/su_host_registered.c`: the target-set loop of `su_host_register_operator` now skips the `.hi` partner of
  a valid 64-bit pair (`i++`), and the new `target_lane_ok` helper holds the per-entry rules so the partner is
  checked as a lane too (it used to be checked as a lane of its own on the next iteration).
- `tests/host/test_host_tables_entities.c`: `test_target_64bit_lanes` (a mixed q32 + i64 + u32 target set, accepted,
  read by a cross-table run) and `test_target_64bit_refusals` (unpaired, wrong-id, wrong-type, trailing and
  writable-`.hi` refusals); both called from `main`.
- `include/sutekh/host.h`: the "cross-table host operators" section states the pair rule for a q32/i64 target lane.
- `docs/MULTI_TABLE_WORLDS.md` (section 8.2), `docs/IMPLEMENTATION_STATUS.md` (a dated section), this handoff.

## The bug

`su_host_register_operator` validated a target set entry by entry. A 64-bit entry was checked to be followed by
`id + 1` with the same type, but the loop did not skip that partner, so the next iteration read the `.hi` entry as a
new lane and refused it: `SU_E_INVALID_ARGUMENT: target field N is a 64-bit lane: the next entry must be id + 1 with
the same type`. Every target set that carried a q32 or i64 lane was therefore refused, so a cross-table operator
could not read 64-bit geometry (positions, velocities, rotations) from its target table. `check_fields`, the own-field
check in the same file, already skips the partner.

## The fix

- The pair check is unchanged: the next entry must exist, be `id + 1` and have the same type, else the existing
  message and `err->index` (the pair's low entry).
- After a valid pair the loop validates the partner with the same per-entry rules (identifier name, `reserved` 0,
  `access` read, a known type, a nonzero id) and then skips it. This is not a new rule: the partner used to go
  through those checks on the next iteration, and skipping it without them would have accepted a writable `.hi`
  half. A violation reports the existing read-only-lane message at the partner's index.
- Every other target-set rule, message, index and hash is untouched. `target_fields` still feeds the same semantic
  hash and identity fold, so a world without a 64-bit target lane keeps its identity and digests.

## Tests

`tests/host/test_host_tables_entities.c`:

- `test_target_64bit_lanes`: registers `game.wide_reach`, whose target set is the q32 pair `pos_x.lo`/`pos_x.hi`
  (ids 10/11), the i64 pair `clock64.lo`/`clock64.hi` (20/21) and the u32 lane `team` (30). The target table
  (`demo.wide`) carries those lanes and two rows with known values (a q32 with both words nonzero, a negative i64, a
  team). One tick runs the operator across tables: the run sees five target columns, reassembles both 64-bit pairs
  (`hi << 32 | lo`) and the test asserts the exact values, that both target rows are alive, that the lane pairs are
  named `pos_x.hi` (11) and `clock64.hi` (21) in the target table, and that the q32's low word reaches the
  operator's own table through `su_host_read_in`. Reading the pair in the wrong order or with the wrong lanes fails.
- `test_target_64bit_refusals`: an unpaired pair (a u32 lane where the `.hi` belongs), a `.hi` at `id + 2`, a `.hi` of
  another type, a trailing 64-bit lane with no partner after it (index 1) and a valid pair whose `.hi` is not
  read-only. The first four expect `SU_E_INVALID_ARGUMENT`, the existing pair message and `err->index` 0/0/0/1; the
  last expects the existing read-only-lane message at index 1. The registry count is unchanged afterwards.

Non-vacuity checked by hand: on the unfixed code the accepted case fails with the issue's message
(`target field 1 is a 64-bit lane: ...`), and with the `i++` but without the partner check the writable-`.hi` case is
accepted (4 failing checks), so both halves of the fix are covered.

- The sanitizer lane ran with Clang: this machine's GCC 16 has no ASan runtime installed (its `libasan.so` is a
  linker script pointing at a library that is not present), so `-DSUTEKH_SANITIZE=address,undefined` with GCC could
  not link. GCC was verified as a plain Release build.
- `tools/validate_pack.py` skipped its optional JSON-Schema section (the `jsonschema` package is not importable under
  `python3 -I` here); the standard-library checks ran and the committed report was not stale, so `--write-report` was
  not needed (it refuses to write a skipped schema result).
- The renderer, the glTF importer, the window tests and `SUTEKH_NATIVE` were not built here (no Vulkan/SDL3 headers,
  native off); CI covers them.
