## What the tests cover
- SHA-256: NIST vectors for "" and "abc", the 448-bit two-block message, and one million 'a' fed in 1000-byte pieces.
- JSON: duplicate keys (with pointer), syntax errors outranking duplicates, malformed UTF-8 (overlong, surrogate, above U+10FFFF), `\u0000` and lone surrogates, exact integers (2^32-1, 2^32, 2^64-1, 2^64 overflow, -1, 1.5, 1e3, -0), depth 32 accepted and 33 rejected, 256 KiB + 1 rejected.
- Valid documents: `examples/movement.*` (field table, instruction words, register count), `examples/movement_v2`, `tests/fixtures/t02/movement.*`, all six `tests/fixtures/t03/*`.
- Manifests: all 7 cases in `tests/fixtures/negative_cases.json` and all 7 in `examples/negative_cases.json`. Each must return exactly its `expected_code` (compared by `su_status_name`). Every file in `tests/fixtures/invalid/` and `examples/invalid/` is reached through a manifest.
- Semantic hash identity: compact, key-reordered `movement.lir.json` gives the same semantic hash and a different source hash. Reversed capsule declaration order, renamed fields and a changed `layout_generation` give the same semantic hash and a different capsule hash.
- Inline cases for stage order and rules: missing store, select on u32 condition, eq on bool, unknown load field, unknown instruction key, unknown top-level key before unknown opcode, duplicate key before undefined register, unsupported profile, query mismatch, second store, undefined register, constant as string.

## Interpretations and contradictions (no fixture was edited)
1. **Brief vs contract/fixtures (numbers).** The brief says the parser rejects negative, fractional and >2^32-1 integers. Contract r3 puts constant range errors in stage 6 as `SU_E_TYPE`, and `negative_u32`, `fractional_constant` and `constant_4294967296` expect `SU_E_TYPE`. Rejecting them in the parser would give `SU_E_PARSE`, which breaks those fixtures. Implemented: the parser accepts any JSON-grammatical number exactly; `su_json_get_uint()` plus the u32 range check gives `SU_E_TYPE`. This needs the coordinator's ruling if the brief's wording was intended.
2. **Stage 1 for the duplicate-key tree.** The parser returns `SU_E_DUPLICATE_KEY` with a complete tree, so the verifier can apply the stage-1 instruction count (4096) and capsule field count (256) before duplicates are reported. No fixture covers this combination.
3. **Stage placement not spelled out by r3:**
   - Field-level capsule shape (id, name pattern, type "u32", read/write booleans, field count 1..256) is stage 4 (`SU_E_TYPE`). The field count above 256 is stage 1.
   - Unsupported `ir_version`, `capsule_format` and `numeric_profile` values are stage 4 (`SU_E_TYPE`). A profile mismatch between IR and capsule is stage 5 (`SU_E_SCHEMA_MISMATCH`).
   - Register operand type mismatches are stage 6, inside the instruction, as r3 lists them.
   - `limits.max_instructions` smaller than the IR instruction count is `SU_E_RESOURCE_LIMIT` in stage 5. Contract r3 does not list it.
4. **Store to unknown field.** Load/store of a name not declared in the capsule uses `SU_E_UNDECLARED_READ`/`SU_E_UNDECLARED_WRITE`. The contract does not separately name this case.
5. **Fixture `store_same_field_twice`.** The note calls `SU_E_UNDECLARED_WRITE` a judgment call. r3 section 1 explicitly maps a second store to that code, so it agrees with the contract. No fixture contradicts r3.
6. **Other choices.** `-0` is accepted as 0. `\u0000` is `SU_E_PARSE`, because JSON allows it but the contract says strings contain no NUL. Capsule `limits.max_rows` above 1,000,000 is `SU_E_TYPE`.
