## Findings and deviations (read these first)

1. **The engine verifier refuses the two keys contract 5.5 requires.** `src/ir/su_lir.c` `check_capsule` accepts only the top-level keys of M0 (`check_keys_opt`), so `system_rev` and `capabilities` give `SU_E_TYPE`, "unknown key 'system_rev'". The M3-03a schema edit accepts them, so the schema and the engine disagree. Both paths confirm it: the driver (`VERIFY ERR 2 SU_E_TYPE pointer=/system_rev`) and the binary (`capsule.submit` reply `SU_E_TYPE`). The committed records keep both keys (contract text). The engine verifies a **projection**: the same file with `system_rev` and `capabilities` removed and nothing else changed. The projection is made by `ir_harness.projection`, and the tests assert the refusal and the acceptance. Owner decision needed: accept the two keys in `su_lir.c` (non-semantic, not hashed), or remove them from 5.5. The file is in the `native_core` / shared area, so I did not change it.
2. **Numeric profile name.** The records use `numeric_profile` `u32_mod_v1`, the only value that the engine (`SU_NUMERIC_PROFILE`, `su_lir.c`) and the capsule schema (`const`) accept. Contract 5.5 and OD-9 say `rts_u32_v1`; the M3-03a handoff recorded the same deviation for host records. Owner decision (OD-9).
3. **`tests/schema/test_capsule_schema.py` now fails (not fixed here; out of my write scope).** Its verdict-stability check (`capsule_files()`) scans every `*capsule*.json` outside `capsules/rts/host` and `tests/schema`, so it compares the four new IR records. Under the pre-M3-03a baseline schema they are refused (`system_rev`, `capabilities`), so the check reports `verdict changed for capsules/rts/{goal,combat,move,damage}.capsule.json` (`status: failed`, `mismatches: 4`). The records are valid under the new schema (`test_records.py` checks that), and the check was written for files that existed before M3-03a. Fix: add `capsules/rts` to `NEW_VARIANT_DIRS` in `tests/schema/test_capsule_schema.py`, which is the M3-03a owner's file. Until then this existing suite is red in this tree. The script's JSON report lists these four entries as its only failures (`negative_cases: 35`); I did not separately audit the positive-instance section beyond that report.
4. **10.4 wording "`emit_event` absent" is ambiguous.** Implemented as: a 0.2 module containing `emit_event` with no declared event cap (`max_events_per_row` 0) is refused with `SU_E_RESOURCE_LIMIT` (`emit_event_without_event_cap`). Owner to confirm the intended meaning.
5. **Scene coverage needs long runs.** The mixed bands start about 16,000 units apart with range 256, so no unit fires within 6 ticks. The differential therefore runs `mixed-64` and `mixed-256` for 220 ticks. `mixed-4096` runs 6 ticks: it covers movement and goal only (no fire, arrival or kill). Coverage counts are in `records/differential.json`.
6. **Instruction counts differ from the M3-02 reference programs** because the authoring tool caches constants and field loads (a load sees tick-start values, so reuse is exact). Both are semantically identical: the differential compares them row by row. Counts below are for the committed LIR.
7. **Mutant N14 (extra read `hp` in goal):** caught structurally. Its engine "differential" hit comes from the driver rejecting a call that omits the new field (`SU_E_INVALID_ARGUMENT`), so it is not an independent detection. Recorded as-is.
8. **Two systematic survivors, equivalent by reading the programs** (`SURVIVOR_CLASS` in `test_mutants.py`): `S-move-const@0-1` (the zero constant feeds only `eq(mv_flag, 1)`), and `S-damage-const@1+1` (the one constant is both the kill flag value and the comparison constant). They survived all three input sets. The other 128 systematic mutants are killed.
