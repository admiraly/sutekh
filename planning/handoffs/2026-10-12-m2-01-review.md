# M2-01 migration contract review (r1)

Reviewed: `planning/contracts/M2_MIGRATION_CONTRACT.md` (commit e730672, DRAFT r1), against `planning/contracts/M0_CONTRACT.md`, `M1_NATIVE_CONTRACT.md`, `M2_ENTITIES_CONTRACT.md`, `docs/HOT_RELOAD_AND_STATE.md` sections 3-6, `docs/TEST_SPEC.md` section 5, `docs/DATA_ABI_AND_STORAGE.md`, `ENGINE_CONSTITUTION.md` C06/C09/C10, `MILESTONES.md` M2, and the code named below.
Reviewer: independent verifier. Scope: report only. No edits to `include/` or `planning/contracts/`.

## Verdict: REJECT as written (repair as r2)

The high-level shape (validate, plan, prepare aside, commit at a boundary, pinned rollback checkpoint) matches C06/C09 and the hot-reload doc. The contract is not implementable without guessing in its core, because it assumes a schema model the code does not have. Four items (B1-B4) are contradictions with existing code or the M0 contract. Several rules cannot be implemented as written (B5-B9). Each blocking item needs a wording change or an owner decision before M2-01 implementation starts.

## Blocking

**B1. The world schema is not "the first capsule's field table".**
- Contract section 1 says the world schema is "the field table of the world's first installed capsule (M0_CONTRACT section 2)". M0_CONTRACT line 26 says the first capsule binds fixture names, but the code does not do that.
- `su_sched_finalize` builds the world table as a **union** over all installed systems (`union_add` ORs `access` per id). `su_sched_check_candidate` then requires each candidate's fields to exist in that table with the same id, type and name.
- Consequence: "the migration edits that table" is ambiguous. Remove-field, the "field_in_use" check and the `compatible`/`broken` classification all depend on whether the schema is the union or the first capsule.
- Wording: "The world schema is the union of the field tables of all installed systems, as in `su_sched_finalize`. Each field's `(id, type, name)` is fixed when first installed; its access is the union of installed capsules' access. M0_CONTRACT section 2 is amended to say the same (owner approval, shared contract)."

**B2. Layout generation is single-valued per schedule; compatible systems cannot "keep running without resubmission".**
- `su_sched_add` (`schedule.c`, `s->count == 0` branch sets `layout_generation` from the first module; later modules must match, else `SU_E_SCHEMA_MISMATCH`). `su_sched_check_candidate` rejects any `gen != s->layout_generation`. `reload.c` reads `layout_generation` from the capsule file.
- Section 4.4 "rebind every installed system whose field table is still valid" and section 5 "compatible systems keep running without resubmission" leave a capsule file that declares generation 1 installed in a generation-2 world. Recovery (section 7) re-reads capsule bytes from the content store, so `su_sched_add` would fail with `SU_E_SCHEMA_MISMATCH` during replay.
- Wording (pick one, owner decision): (a) "A committed migration requires every installed system to be resubmitted with `layout_generation = to_layout_generation`; a system not resubmitted is `needs_review` and is not run." This is the simplest and is what I recommend for M2-01. (b) "Compatible systems keep their capsule; the migration record stores `{system_id, capsule_hash, bound_layout_generation}` in `migration_lineage`; recovery applies the same mapping before `su_sched_add`." Option (b) also needs a change to `su_sched_add` and `su_sched_check_candidate`, which the contract does not mention.

**B3. A transform cannot be verified against two field tables with the existing verifier.**
- `su_lir_verify(capsule, capsule_len, lir, lir_len, out, diag)` takes one capsule. Field names bind to that capsule's own table (`find_field`, `su_lir.c` stage 6), and `m->fields` / `SuInsn` operands are indices into that one table.
- A transform needs a read index space (source table) and a write index space (destination table). Section 2 does not say which capsule document describes the source and destination, and does not define a new verifier entry point.
- The VM invocation (`SuInvocation` / `SuOutputs` in `abi.h`) binds views by one table, so writing into new column storage needs an ABI change. `abi.h` is owner-approved.
- Wording: "A transform is a `transform_format` 0.1 document `{source_fields: [...], fields: [...]}` (both tables, same field-object shape as a capsule), with its IR `query` equal to the world schema. `su_lir_verify_transform(src_capsule, dst_capsule, lir, ...)` is a new entry point (new owner-approved header). Reads index `source_fields`; stores index `fields`; each destination id is written at most once. The VM binding change is an `abi.h` change (owner approval) and is listed in the handoff." Until then, the transform path is not buildable.

**B4. Rename is classified by id/type but enforced by name, and the error code is wrong.**
- Section 2 says `rename_field` "fixtures/IR referring to the old name fail verification afterwards (`SU_E_UNDECLARED_READ/WRITE`)". The capsule verifier never sees the world schema, so an old-name capsule verifies cleanly. The failure happens at `su_sched_check_candidate` / `union_add`, which compare names and return `SU_E_SCHEMA_MISMATCH`.
- Section 3 classifies a system as `compatible` when "all its fields still exist with same id/type". A renamed installed system is therefore reported `compatible` but would fail `su_sched_check_candidate` on recovery.
- Wording: "`compatible` requires same id, type and name. A rename makes every installed system that reads or writes the field `needs_review` (not `compatible`) until resubmitted. Errors for old-name capsules: `SU_E_SCHEMA_MISMATCH`."

**B5. "Field IDs are never reused" cannot be enforced across restart.**
- Section 2 requires that a removed id is not reused "while retained checkpoints reference it". That is a weaker rule than "never reused within a lineage", and the contract uses both.
- The data needed to enforce it does not exist: snapshot 0.2 `fields` lists only live fields, `su_world_canonical_*` (encoding v2) lists only live fields, and `SuWorldDesc` has no retired-id list. After a restart, nothing remembers a removed id.
- Wording: "Each world lineage keeps `retired_field_ids` (ascending u32 list). `add_field` rejects any id in that list (`SU_E_SCHEMA_MISMATCH`). The list is written into the snapshot and into the recovery log. It is never shrunk within a lineage." The snapshot key and canonical-encoding change is listed under B7 and B8.

**B6. Permission flags and zero-access fields.**
- Section 2 says `read`/`write` are "capsule metadata only and are not stored in the world schema". But `su_world_create` requires nonzero access (`su_world.h`: `SU_E_INVALID_ARGUMENT` for "empty/invalid access"), and writable columns need a staging column (`su_world.h` build_outputs). A field added with no capsule using it has no valid access value.
- The `add_field` op also accepts `read` and `write` keys, which the contract says are ignored. An implementer cannot tell whether they are validated.
- Wording: "The `add_field` `read`/`write` keys are **rejected** if present (`SU_E_TYPE`). World access for a field is the union over installed capsules, which may be `0` only for a field no installed capsule uses. `su_world_create_ex` must accept access `0` for a field that no installed capsule uses; today it rejects that (`su_world.h`), so this is a change to `su_world.h` (owner approval). Until a capsule uses the field, `world.inspect` reports `access: 0`."

**B7. Snapshot header: "optional keys" contradict the strict parser, and `layout_generation` already exists.**
- `k_top_01` and `k_top_02` (`snapshot.c` lines ~21-29) list every top-level key, and `layout_generation` is already a required key in both (and is checked against the target world in restore, `snapshot.c` ~988-996).
- `check_keys` (`snapshot.c` ~697-711) requires `obj->u.object.count == nkeys`, so an absent optional key is a parse error. "Absent = generation 1, empty lineage" cannot be implemented without a new parser.
- There is no "world header" object in snapshot 0.2; the keys are top-level.
- There is no 0.2 golden fixture. `tests/fixtures/snapshot01/golden_0_1.json` is the only golden, and it is 0.1. The contract's "key order is fixed in the worked example fixture" points at a file that does not exist.
- Wording: "Snapshot 0.3 (owner approval; `SU_SNAPSHOT_FORMAT_03 "0.3"`) adds exactly one required top-level key `migration_lineage` (array of `migration_hash`, possibly empty) and `retired_field_ids` (B5). Key order is `... "layout_generation", "numeric_profile", "fields", "semantic_manifest", "entity_ids", "columns", ... "migration_lineage", "retired_field_ids"`. 0.2 keeps its current key set and remains accepted by restore with generation 1, empty lineage, empty retired list. A golden 0.3 fixture is added to `tests/fixtures/snapshot03/` in the same change." The contract must say which version `world.snapshot` emits after M2-01 is enabled (disabled-by-default implies 0.2 until enabled).

**B8. The recovery digest does not cover the layout, and the replay invariant rejects a migration.**
- Canonical encoding v2 (`su_world.h`) is `"SUWSTATE" | version | tick | field_count | entity table | fields`. It contains no `schema_id`, no `layout_generation` and no field names. A rename-only or generation-only migration leaves the state hash unchanged, so the digest check in recovery cannot detect it.
- `sync_after` (`su_agent.c`, LOG_STEP branch) requires `rev_new - w->rev == tick_new - w->tick`. A migration commit bumps the revision with no tick change, so it fails that invariant. No migration log kind exists (`LOG_NONE`, `LOG_STEP`, `LOG_INSTALL`, `LOG_SPAWN`, `LOG_DESPAWN`).
- Wording: "The migration digest is `SHA-256(canonical_state || layout_generation_u32 || schema_descriptor_sha256)`, where the schema descriptor is the sorted `(id, type, name, access)` list. The recovery log gains kind `LOG_MIGRATE` (commit) and `LOG_ROLLBACK`, each with `rev` delta 1 and `ticks` delta 0. `sync_after` accepts that pair only for these kinds." `LOG_*` kinds are in `su_agent.c`, not in a shared header, so this is a recovery-design change owned by the agent owner.

**B9. "Checkpoint immediately after commit is mandatory" conflicts with the agent's current handling of checkpoint failure.**
- `sync_after` (`su_agent.c` ~1113-1120): when `checkpoint_world` returns `CK_NOROOM`, the code sets `rc = CK_OK` and logs "the operation is applied and logged; the log keeps it until a later checkpoint".
- Wording: "After a successful commit, the post-commit checkpoint must succeed before `world.migrate_commit` replies. If it returns `CK_NOROOM`, the commit is refused by rolling back to the pre-migration checkpoint (pinned in B10) and the reply is `SU_E_RESOURCE_LIMIT` with reason `post_commit_checkpoint`. A commit without a durable post-commit checkpoint is never acknowledged." Alternatively, the owner accepts log-only durability for M2-01 and removes the word "mandatory".

**B10. The pinned pre-migration checkpoint is JSON and can exceed the default spool.**
- Checkpoints are snapshot documents (`checkpoint_world` calls the worker snapshot path). Columns are JSON integers keyed by name. A decimal u32 value is 1 to 10 digits plus a separator. Estimate from the emit format, not measured: about 2 to 11 bytes per value, so about 2 to 11 MB per column at 1,000,000 rows.
- The default spool is `AGENT_DEFAULT_SPOOL` = 32 MiB (`su_agent.c:61`). After commit, the pinned pre-migration checkpoint and the mandatory post-commit checkpoint both exist, and `committed_bytes` counts both.
- Wording: "The commit reserves `pre_migration_bytes = snapshot_bytes(pre)` plus `post_commit_bytes_bound = snapshot_bytes(post)` before preparation (both are estimates from row count and field count, bound at plan time). If `budget_admits` fails, the plan is `valid: false` with `resource.reason = "spool_budget"`. Commit is refused with `SU_E_RESOURCE_LIMIT` and the old world is unchanged. The 1,000,000-row case is reported as admitted or refused, with the bound used, not assumed."

**B11. `SU_EVENT_MIGRATED` does not exist.**
- `include/sutekh/entities.h` defines `SU_EVENT_REJECTED` (`0xFFFFFFFF`), `SU_EVENT_SPAWNED` (`0xFFFFFFFE`), `SU_EVENT_DESPAWNED` (`0xFFFFFFFD`) and reserves kinds `>= 0xFFFFFF00`. A grep of `include/` and `src/`/`tests/` for `MIGRATED` and `migrate` returns nothing.
- Wording: "Owner adds `SU_EVENT_MIGRATED UINT32_C(0xFFFFFFFC)` to `entities.h` (inside the reserved range). `a` = from layout generation, `b` = to layout generation. The event is emitted at the commit's canonical position (after IR commands of that boundary), consumes `event_seq`, and is not counted against `max_events_per_tick`."

**B12. Defaults versus zero for spawn and for rows above `high_water`.**
- Section 2 fills the new column with `default` for "all capacity rows except dead entity slots". Canonical encoding v2 writes only `values[high_water]`; rows at or above `high_water` are implicitly zero. Filling capacity rows contradicts that encoding.
- `su_world_spawn` (`su_world.h`) writes the given values and "all other fields 0". After a migration, a control-plane spawn gives a new field the value 0, not its default. The contract does not say which applies.
- Wording: "New-column default applies to alive slots below `high_water` only. Rows at or above `high_water` remain implicitly zero. Spawn after an additive migration writes the field's `default` for every field not named in the request (this changes `su_world_spawn`'s contract; owner approval)." Add a test: spawn after migration gets `default`.

**B13. Native retirement is not named and the install check is state-based.**
- The registry in `native_versions.c` is keyed by `seq` and global, not by world. `su_nv_release` (line ~825) sets `RETIRING` and frees only when `inflight == 0`, which gives the deferred retirement the contract wants. `su_nv_install` (line ~508) checks only `state == ADMITTED`, not the layout generation.
- Wording: "Migration commit calls `su_nv_release(seq)` for every artifact whose `layout_generation != to_layout_generation`, including artifacts that are `ADMITTED` but not yet `INSTALLED`. `su_nv_install` refuses any artifact not in `ADMITTED`. Retirement is deferred to quiescence (`inflight == 0`). Tests: a specialize started before commit cannot install after it."

**B14. `world.inspect` fields are not in the contract's list.**
- `h_world_inspect` (`su_agent.c` ~2853) allows `world_id, fields, limit, offset, entity`. Section 5 says `needs_review` is "flagged in `world.inspect`" but names no key, value or shape. Section 3 adds `schema_before/after` only to the plan.
- Wording: "`world.inspect` adds `layout_generation` (u32), `migration_lineage` (array of hash), and per-system `needs_review` (bool) with `reasons[]`. Keys are read-only and the allowed-key list in `h_world_inspect` is extended in the same change."

## Non-blocking

- Plan memory accounting: section 3 says `bytes_peak` includes staging and transform scratch but does not give the formula. For a world with `n` rows, `k` writable columns and `m` new columns, committed + working + staging is `12 * n * k` bytes, the new storage is `4 * n * m`, and the pre-commit checkpoint is the JSON estimate in B10. At 1,000,000 rows this is the number the plan must report. The formula should be written down. These are derived from the storage types, not measured.
- Transform copy semantics (section 2: "keep value if existed before"): the contract should say the copy happens before the transform runs, and that a field both copied and written is an error.
- Rollback content store: section 6 re-installs pre-migration systems from the content store. Under B2 option (a) those capsules are replaced by resubmission; the content store must keep the pre-migration capsule bytes for as long as the pinned checkpoint lives. Say so.
- Error mapping: `SU_E_TYPE` for a `to_layout_generation != from + 1` is better as `SU_E_SCHEMA_MISMATCH`; `SU_E_TYPE` is used for document shape only.
- `deterministic` transform replay on another backend: section 7 says replay "fails closed" on a build that cannot reproduce the schema, but not on a build with a different backend. C08 requires the semantic hash, not the backend, to match; say so.
- Event log for migration: the event kind (B11) is in the reserved range, so the rule that engine events cannot appear as IR constants must be restated for the migration path.
