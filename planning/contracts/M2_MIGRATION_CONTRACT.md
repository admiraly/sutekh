# M2-01 contract draft r2: schema migrations (additive and explicit destructive)

Status: DRAFT r2 (contingent on M1 owner acceptance; additive, disabled by default until a world performs its first migration). r1 was REJECTED by the independent review (`planning/handoffs/2026-10-12-m2-01-review.md`, 14 blockers); r2 resolves each (B1..B14 cited inline). Builds on M2-00 (entities, snapshot 0.2, recovery log). Header addition: `SU_EVENT_MIGRATED` = 0xFFFFFFFC in `entities.h`. M0_CONTRACT section 2 is amended (B1). `abi.h` is NOT changed. A change after acceptance needs a new generation.

## 1. Principles
- A migration is a **transaction on one world**: validate -> plan (with resource admission) -> prepare the new representation aside -> controlled commit at a quiescent boundary -> publish a new layout generation and world revision, or fail with the old world untouched (C06, C09). Its cost is reported separately from code reload.
- **World schema** (B1): the union of the field tables of all installed systems (`su_sched_finalize`). A field's `(id, type, name)` is fixed when first installed; its access is the union of installed capsules' access. A field no installed system uses is stored with storage access READ (so no `su_world` change is needed, B6) and reported with `used:false`.
- Field ids are stable identity and **never reused within a world lineage** (B5): the world keeps `retired_field_ids` (ascending u32 list, never shrunk) persisted in snapshot 0.3 and the recovery state.
- Noninvertible changes are rolled back only by restoring the retained pre-migration checkpoint, never by a guessed inverse.

## 2. Migration document (strict JSON; same strictness as IR)
```json
{ "migration_format": "0.1", "id": "m-001", "from_layout_generation": 1, "to_layout_generation": 2,
  "ops": [ {"op":"add_field","field":{"id":3,"name":"health","type":"u32","default":100}},
           {"op":"rename_field","id":1,"new_name":"x"},
           {"op":"remove_field","id":2},
           {"op":"transform","document":"transform.json"} ] }
```
- <= 64 ops, <= 256 KiB, depth <= 16. `from_layout_generation` must equal the world's current generation (`SU_E_STALE_REVISION`); `to` must be exactly `from + 1` (`SU_E_TYPE`).
- `add_field`: new unique id not currently used and not in `retired_field_ids` (`SU_E_SCHEMA_MISMATCH`), unique name, `type` `"u32"`, required `default` (u32). `read`/`write` keys are **rejected** if present (`SU_E_TYPE`) (B6). The default is stored per field in the world schema (snapshot 0.3 `fields[].default`, absent/`0` for pre-existing fields). **The new column is filled with `default` for alive slots below `high_water`; rows at or above `high_water` and dead slots stay implicitly zero** (B12). After the migration `world.spawn` writes each field's `default` for every field not named in the request (this amends M2-00 spawn: previously 0; fields created before any migration have default 0, so existing behaviour is unchanged).
- `rename_field`: same id, new unique name. Every installed system reading or writing the field becomes `needs_resubmission` (B4).
- `remove_field`: refused with `SU_E_UNSUPPORTED_MIGRATION` (reason `field_in_use`) if any installed system reads or writes it, unless that system is listed in `drop_systems` of the commit (section 4). The id enters `retired_field_ids`.
- `transform` (**explicit destructive path**, the only way to change values or retype; B3 resolved WITHOUT a verifier or ABI change): `document` is a `transform_format` 0.1 file `{ "transform_format":"0.1", "source":"transform.lir.json", "writes":[<field ids>] }`. The engine **synthesizes an in-memory capsule** whose field table is the union of the source and destination schemas: an id present in the source is readable; an id in `writes` is writable (an id may be both: the transform reads the OLD value and stores the NEW value); ids in `writes` must exist in the destination schema, types must agree for ids present in both (retyping beyond u32 is out of scope). The unchanged `su_lir_verify` verifies the transform against that capsule (so "every writable field is stored exactly once" holds for `writes`). The IR is IR 0.1 only (no entity ops). Execution: the reference VM runs it over alive rows below `high_water` with input views on the OLD columns and output views on the NEW column storage; binding layout generations are synthetic labels (`from_layout_generation` for both sides). Destination fields NOT in `writes`: copied from the old column if the id exists in the old schema, else `default`. A transform with `writes` ids that are not alive in the destination schema is a verification error (`SU_E_SCHEMA_MISMATCH`).
- Errors/limits: transform <= 4,096 instructions; fields per schema <= `SU_LIMIT_FIELDS` (256).

## 3. Plan and admission (`world.migrate_plan`)
`world.migrate_plan {world_id, expected_world_revision, migration_path | migration (inline <= 256 KiB)}` -> `{plan_id, plan_hash, migration_hash, from_layout_generation, to_layout_generation, schema_before, schema_after, columns_added, columns_removed, columns_renamed, transform: {semantic_hash}|null, resource: {bytes_new_columns, bytes_peak, pre_migration_bytes, post_commit_bytes_bound, rows, reason?}, systems: [{system_id, impact: "compatible_after_resubmit"|"needs_resubmission"|"broken", reasons[]}], valid: bool}`.
- "compatible" means the system's field `(id, type, name)` still exist unchanged; **every** installed system still needs resubmission after a layout change (B2, next section). `broken` = uses a removed field. `needs_resubmission` = uses a renamed/transformed field or any other impact. Old-name capsules fail with `SU_E_SCHEMA_MISMATCH` (B4).
- Resource admission (B10): the plan reserves `pre_migration_bytes = snapshot_bytes(pre)` plus `post_commit_bytes_bound = snapshot_bytes(post)` plus new columns plus scratch, estimated from row count and field count (estimate stated as such); if `budget_admits` fails the plan is `valid:false` with `resource.reason = "spool_budget"` or `"memory"` and the exact numbers; commit is refused (`SU_E_RESOURCE_LIMIT`). The real `sutekh` binary's spool default is 512 MiB (library default 32 MiB); the 1,000,000-row case is reported as admitted or refused with the bound used, never assumed.
- A plan is immutable and bound to `(world_id, world_revision, from_layout_generation)`; it goes stale when the revision changes.

## 4. Commit (`world.migrate_commit`) (B2)
`world.migrate_commit {world_id, plan_id, expected_world_revision, resubmit:[<candidate_id>...], drop_systems?:[<system_id>...]}`.
- **Every installed system must be either replaced by an already-submitted, already-evaluated candidate of the same `system_id` whose capsule declares `layout_generation = to_layout_generation`, or listed in `drop_systems`.** The candidates are verified against the post-migration schema before anything changes. A missing/extra replacement, or a system left neither replaced nor dropped, refuses the commit (`SU_E_UNSUPPORTED_MIGRATION`, reason `systems_unresolved`) with the old world untouched. There is therefore no state in which an old-generation system is installed in a new-generation world.
- Steps: (1) revalidate plan/revision/generation (`SU_E_STALE_REVISION`); (2) pin a **pre-migration checkpoint** (snapshot bytes in the spool); (3) prepare aside: allocate the complete new column storage and a new schedule built from the replacement candidates, fill defaults, run the transform, run self-checks (row counts, entity table untouched, dead rows zero); any failure including allocation failure discards everything and the old world is bit-identical and active; (4) commit at a tick boundary, never mid-tick: swap storage + schema + schedule, `layout_generation = to`, extend `retired_field_ids` and `migration_lineage`, bump the world revision, retire native artifacts (below), invalidate in-flight specializations, emit `SU_EVENT_MIGRATED` at the commit's canonical position (after IR commands of that boundary; consumes an `event_seq`; not counted against `max_events_per_tick`) (B11); (5) **post-commit checkpoint must succeed before the reply**; if it returns no-room the commit is rolled back to the pre-migration checkpoint and the reply is `SU_E_RESOURCE_LIMIT` reason `post_commit_checkpoint`: a commit without a durable post-commit checkpoint is never acknowledged (B9).
- **Native** (B13): the commit calls `su_nv_release(seq)` for every artifact of the world whose `layout_generation != to_layout_generation`, including `ADMITTED` ones; `su_nv_install` refuses any artifact not `ADMITTED` and any whose generation differs from the schedule's; retirement is deferred to quiescence (`inflight == 0`). A specialize begun before the commit can never install after it.
- Reply: `{world_revision, layout_generation, migration_hash, timings:{plan_ns,prepare_ns,transform_ns,swap_ns,checkpoint_ns,total_ns}, bytes:{new_columns,peak}, systems:[...], rollback_available:true}`. Migration timings are never merged into code-reload latency.

## 5. Rollback (`world.migrate_rollback {world_id, expected_world_revision}`)
Restores the pinned pre-migration checkpoint (schema, defaults, retired ids, layout generation, schedule from the checkpoint's system manifest, entity table, event log), assigns a NEW world revision (`restored_from` = the migration), retires native artifacts, and re-installs the pre-migration systems from the content store. Changes made after the migration are **lost** (it is a restore, not an undo) and the reply says so. Available while the pinned checkpoint is retained (until the next migration commit or `world.close`; evicted -> `SU_E_STALE_REVISION` reason `rollback_unavailable`). `retired_field_ids` is NOT shrunk by rollback: a rolled-back lineage keeps the ids retired by the undone migration (monotonic lineage).

## 6. Snapshot 0.3, digest and recovery (B5, B7, B8, B9)
- **Snapshot 0.3** (`SU_SNAPSHOT_FORMAT_03 "0.3"`): a new strict format; `world.snapshot` emits 0.3 **only when the world's lineage is non-empty** (it has migrated) and 0.2 otherwise (so every existing 0.2 golden/fixture is unchanged); restore accepts 0.1, 0.2 and 0.3. 0.3 = the 0.2 key set, with `fields` entries `{id,name,type,default}`, plus two required top-level keys appended after the 0.2 keys in this order: `migration_lineage` (array of `migration_hash`) and `retired_field_ids` (ascending array). A worked golden is added at `tests/fixtures/snapshot03/` with the migration that produces it. Restore of a 0.3 snapshot restores schema, defaults, layout generation, lineage and retired ids (it is the only restore allowed to change the schema, via `world.migrate_rollback` / recovery).
- **Digest** (B8): the recovery digest becomes `SHA-256(canonical_state || layout_generation_u32_le || schema_descriptor_sha256)` for all worlds (internal, no stored evidence depends on it except test expectations, regenerated and listed), where the schema descriptor hash covers the sorted `(id, type, name, default)` list. Rename-only and generation-only migrations therefore change the digest.
- **Recovery log**: new kinds `LOG_MIGRATE` and `LOG_ROLLBACK`, each a world-revision delta of 1 and tick delta 0; `sync_after` accepts that pair only for these kinds. A `LOG_MIGRATE` entry stores the migration document bytes and the replacement candidates' content hashes (content-addressed spool). Recovery of a migrated world uses a new internal primitive `internal.world.create_from_snapshot` (schema, entity table, columns from the snapshot; systems from the checkpoint's system manifest of capsule/source content hashes) because the original fixture no longer describes the world; the post-commit checkpoint is mandatory (section 4) and is the recovery base.
- Replay logs record the migration hash and effective tick; a replay on a build that cannot reproduce the same schema fails closed.

## 7. Inspect (B14)
`world.inspect` adds read-only keys `layout_generation`, `migration_lineage[]`, `schema:[{id,name,type,default,used,access}]`, and per-system `needs_resubmission`/`reasons[]` never persists (there are none after a successful commit by section 4); the allowed-key list in the handler is extended in the same change. `world.migrate_plan` shows pre-commit impact.

## 8. Entity worlds, events, tick workers, chunk buffers
Migration operates on the entity world as a whole: capacity, entity table, generations and event log are untouched (only columns, schema and schedule change); per-chunk command/event buffers are re-sized for the new schedule at commit using the M2-00 admission formula (refused at plan time if over budget); tick workers need no change (they read the schedule at the next tick). Zero-row and zero-alive worlds are valid migration targets.

## 9. Errors and limits
Document errors use `SU_E_PARSE/TYPE/DUPLICATE_KEY` with the M0 stage order (limits, parse, duplicate keys, shape, semantics, ops in order). `SU_E_STALE_REVISION` (generation/revision/plan), `SU_E_SCHEMA_MISMATCH` (ids, names, types, retired ids, old-name capsules), `SU_E_UNSUPPORTED_MIGRATION` (`field_in_use`, `systems_unresolved`, broken systems, unsupported op), `SU_E_RESOURCE_LIMIT` (admission, post-commit checkpoint), `SU_E_CANDIDATE_FAILED` (transform/verification failure with the failing op). Rows <= `SU_LIMIT_ROWS`.

## 10. Tests required for acceptance
Additive default fill (alive below high_water only; dead and above-high_water zero), spawn after migration gets defaults, rename keeps id and old-name capsules fail with `SU_E_SCHEMA_MISMATCH`, remove rejected while used and allowed when dropped/unused, field id reuse refused across restart (snapshot 0.3 + recovery), transform vs an independent Python model (wrap/overflow, copy semantics, read-old/write-new on the same id), memory failure injected at each allocation point leaving the world bit-identical and active, post-commit checkpoint failure rolls back, rollback restores schema+state exactly and says what is lost, layout invalidation (native artifacts retired, a specialize in flight cannot install, bindings regenerated, replacement systems bit-identical to a control world on unaffected data), plan staleness, exact admission numbers, crash recovery before checkpoint, after commit, after rollback (kill the worker at each point; recovered state/digests equal an uninterrupted control run), snapshot 0.2/0.3 compatibility and the 0.3 golden, digest sensitivity to rename-only migration, event `SU_EVENT_MIGRATED` ordering, 1,000,000-row migration timing reported separately from reload, ASan/UBSan/TSan, and mutation proofs for each.

## 11. Open points for the owner
Retyping beyond u32, online migration with write reconciliation (this contract always pauses at a tick boundary), multi-world migrations, destructive entity-table changes, schema downgrade tooling, automatic compatible-system rebinding without resubmission (rejected for M2-01: it needs `su_sched_add`/`check_candidate` changes), snapshot compression for large pinned checkpoints.
